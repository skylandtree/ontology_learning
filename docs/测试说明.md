```bash
node test/run.js
```

环境 Node.js ≥ 22.13（内置 `node:sqlite`），无第三方依赖，约几秒完成。退出码非 0 表示有断言失败。生成四份报告和一份用例清单：

## 四、预期值的来源与独立性

- 数值预期（发现命中日、总下倾、缺口、覆盖半径、Δ、周边影响逐项、效果占比、保护指标）由 `scripts/build-expected.js` 事前算出：它只读种子数据与 SPEC 解析出的门限、参数，按 SPEC 公式自行实现，不引用 `src/`。
- 构建器与被测应用由同一团队编写，独立性有限；SPEC 的规则与测试假设经业务确认前，所有预期的业务确认状态均为“待确认”。
- 状态与约束类预期（谁能做什么、什么情况下被拒绝）由 SPEC 的状态机和 INV 直接推出。

## 五、覆盖是怎么统计的

（业务用例的覆盖单独统计：业务用例的前置状态在“setup”上下文里构造，不计入覆盖；只有用例步骤本身触发的函数、动作、约束、规则才计入“业务决策用例”或“业务问答用例”。）

`src/tracker.js` 在存储层、函数层、动作层、问答层埋点：对象读写记对象类型，关系读写记关系类型，函数调用记函数，动作入口记动作，约束校验记 INV（并区分“通过”与“违反”），规则与测试假设在被应用时记录。场景运行时分别标记为“决策”或“问答”。测试读取这些记录核对每个 SPEC 要素，并输出覆盖矩阵。

## 六、手工验证

```bash
node src/qa-cli.js --stage fresh
```

从只有前置数据、没有工单开始，可以一步步走：

1. `9月11日哪些小区弱覆盖？`——看到 F_12 的发现清单，此时没有任何工单；
2. `请对崇贤达NF02H_222建单`——优化本体执行 A_01，回答里标出本次写入；
3. `请对它定因`——A_02 调 F_07、F_08；`它的根因是什么？`；
4. `帮我确认这张工单`——只提示须人工，不代办（需要地市优化工程师，且部分重合时须写复核判断）。

人工角色的动作经本体后端接口执行。服务有自己的存储，从同样的种子和时钟（2026-09-11 09:00）开始，可以完整走一遍：

```bash
node src/server.js --port 27072
```

Base URL 是 `http://localhost:27072/agent-onto-harness`，每次请求带三个头（规范 1.2）：`currentnetuserid`（用户）、`x-sys-code`（系统＋租户）、`x-context-key-groups`（角色，逗号分隔，可 URL 编码）。

```bash
B=http://localhost:27072/agent-onto-harness/api/v1/osdk
H='-H "currentnetuserid: eng-01" -H "x-sys-code: data" -H "x-context-key-groups: %E4%BC%98%E5%8C%96%E6%9C%AC%E4%BD%93"'
curl "$B/ontologies" -H "currentnetuserid: eng-01" -H "x-sys-code: data"
curl "$B/shwo-weak-coverage/objectTypes/OT_CELL_MR" -H "currentnetuserid: eng-01" -H "x-sys-code: data"
curl -X POST "$B/shwo-weak-coverage/actions/A_01/execute" -H "currentnetuserid: bot" -H "x-sys-code: data" \
  -H "x-context-key-groups: %E4%BC%98%E5%8C%96%E6%9C%AC%E4%BD%93" -d '{"params":{"cellKey":"LTE:156514014"}}'
curl -X POST "$B/shwo-weak-coverage/actions/A_02/execute" -H "currentnetuserid: bot" -H "x-sys-code: data" \
  -H "x-context-key-groups: %E4%BC%98%E5%8C%96%E6%9C%AC%E4%BD%93" -d '{"params":{"ticketNo":"TK-LTE-156514014-001","mode":"rule"}}'
curl -X POST "$B/shwo-weak-coverage/actions/A_03/execute" -H "currentnetuserid: eng-01" -H "x-sys-code: data" \
  -H "x-context-key-groups: %E5%9C%B0%E5%B8%82%E4%BC%98%E5%8C%96%E5%B7%A5%E7%A8%8B%E5%B8%88" \
  -d '{"params":{"ticketNo":"TK-LTE-156514014-001","decision":"确认","reason":"告警仅占1/7命中日，复核通过"}}'
```

响应统一是 `{code:0, message:"success", data, traceId}`；错误是 `{error:true, code, status, message, errorCode, traceId}`，`errorCode` 取值见 `GET $B/errorCodes`（缺认证头→401 UNAUTHENTICATED，角色无权→403 PERMISSION_DENIED，约束拒绝→409 INV_xx，对象不存在→404 OBJECT_NOT_FOUND）。

`x-context-key-groups` 直接用角色名（URL 编码）即可，也接受 `bot`／`engineer`／`supervisor`／`field`／`expert`／`knowledge` 这类英文键。

## 七、业务用例

业务用例按“谁、在什么状态下、做什么或问什么”组织，和上面按 SPEC 用例（TC）组织的决策场景互补，共用同一套代码与种子数据。完整清单见 `docs/业务测试用例.md`（自动生成）。

- **起始状态**：清晨、工单待核验、已定因、已确认、方案待确认、已派单、已回填、第1周已评估、持续有效、已关单入库。每个状态是前一个状态再走一步，由优化本体和各角色通过动作入口走到（不是直接写库）；个别用例改一条事实（例如天线挂高为空、某小区目标半径 560 m、某天的 MR 更正），在用例里明写。
- **步骤**：推进时钟、某角色执行动作（预期成功＋核对，或被某个拒绝码拒绝）、某角色提问（口语化提问，核对意图与回答内容）、只读核对。
- **问答的写库约束**：由提问触发的写入只允许优化本体被授权的动作（建单、定因、生成方案、写入效果），每次恰好 1 条审计；“帮我批了”“帮我关单”只得到须人工执行的提示，并按提问者角色说明其是否在 SPEC 允许范围内。
- **回答的边界**：SPEC 没有定义的内容（置信度、预测、下倾以外的措施、NR 公式）如实回答“没有定义”，不编造。
- **变异检查**：人为破坏实现（关单不再要求持续有效、多小区变更不再要求主管批准、假性弱覆盖门限失效、“能不能建单”总答可以）后，对应的业务用例都会失败，说明这些用例不是摆设。
