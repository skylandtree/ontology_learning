# 上海覆盖工单本体决策与问答：案例说明

本文说明这个应用做什么、本体从哪里来、上海 4 张真实工单怎样映射到 SPEC 本体、哪些数据是真实的哪些是构造的，以及主线（崇明 SHCHM）的逐步决策过程。测试方法见 [测试说明.md](测试说明.md)，本体全量定义见 [../ontology/ONTOLOGY.md](../ontology/ONTOLOGY.md)。

## 一、本体从哪里来

本体的全部要素只来自 SPEC（`spec/` 下的 V0.6 副本）：

| 要素 | 数量 | 来源（SPEC 位置） |
|---|---|---|
| 对象类型 | 9：OT_AREA、OT_CELL、OT_CELL_MR、OT_ANTENNA、OT_SITE、OT_TICKET、OT_PLAN、OT_EFFECT、OT_CASE | 3.1 对象类型表；属性来自 3.2 属性表与 4.1 字段字典 |
| 关系类型 | 17：RT_01～RT_17 | 3.3 关系类型表 |
| 函数 | 12：F_01～F_12 | 3.4 函数表；公式与顺序来自“函数填写要求” |
| 动作类型 | 11：A_01～A_11（A_10 只定义） | 3.5 动作表；允许角色取自“发起角色”列 |
| 核心约束 | 17：INV_01～INV_17 | 3.2 约束表 |
| 业务规则 | 19（含只登记的 RULE_M02、M03、W03） | 4.2 规则表；派单门限取自 RULE_D01、D02 原文，D03、D04 同第 2、3 行 |
| 测试假设 | 12：TH01～TH03、TH07～TH09、TH11～TH16 | 4.2 测试假设登记；参数值从表中的取值解析 |
| 措施类型字典 | 2：TILT_UP_MECH、TILT_UP_ELEC | 4.2 措施类型字典 |

`scripts/gen-ontology.js` 解析这些表格生成 `ontology/shwo.ontology.json`，并自检：SPEC 里出现的每个标识都有定义；测试再重新解析一次，要求与 JSON 逐项一致、SPEC 指纹一致。运行期存储层按 SPEC 校验：未定义的对象类型、属性、关系、端点类型一律拒绝。

**上海原有的东西没有进入本体**：ICOS 根因结论里的原因目录（C01～C11）、自优化方案里的参数（qrxlevmin、SSB 功率偏置、各类开关）、原因—措施知识表的 100 行、问题邻区与切换指标等，SPEC 都没有定义，所以本体里没有；它们只留在 `data/source/` 作来源事实。

## 二、业务背景与这次要改变的工作

上海的覆盖类工单由 ICOS 给出根因结论和自动方案，再走自优化闭环或人工闭环。SPEC 要解决的是另一个层面的问题：**弱覆盖问题是不是真的存在，由哪些数据、按哪条规则得出？**因此本体以前置数据——小区逐日 MR 统计——作为问题锚点：

- 派单规则（RULE_D01～D04）作用在 `OT_CELL_MR` 上：单日 RSRP＜-110 的弱覆盖采样点数与占比同时达到门限记“命中”，7 天出现 3 天即达到派单条件；
- `F_12` 对一批小区只读地发现，`A_01` 建单时重算 `F_06` 并把引用的 MR 日统计固定进工单的 `discovery` 快照（RT_17）；
- 工单只是发现之后的处置载体：根因、方案、效果、案例都挂在工单上，工单关闭不改变前置数据。

## 三、数据来源

| 层 | 文件 | 说明 |
|---|---|---|
| 原文 | `data/source/shanghai_tickets.json` | `scripts/extract-source.js` 从 xlsx 逐字抄录（需要 `xlsx` 模块，抄录结果已保存，一般不必重跑） |
| 种子 | `data/seed/*.csv`（14 张表，一表一文件，UTF-8 带 BOM，Excel 可直接打开） | `scripts/gen-seed.js` 生成。**真实事实从原文用正则解析**（覆盖率、站高、方位角、下倾角、告警日期、工单号），其余按真实网管数据的样子补齐；每个站点、天线、小区、区域、现场回填都在 `provenance.csv` 里标注“原文／原文＋构造／构造” |
| 预期 | `data/expected/expected.json` | `scripts/build-expected.js` 独立重算，测试基准 |

**取自原文**：SHCHM 覆盖率 62.72%、站高 38 m、方位角 330°、下倾角 3°→4°、告警 BASE STATION INFORMATION（9 月 7 日）；SHBAO 覆盖率 88.18%；SHYAP 重叠覆盖率 13.88%；4 个工单号；小区名“崇贤达NF02H_222”；覆盖区域“崇明陈家镇陈东路周边”。

**补齐**：站点坐标；同天线小区崇贤达NF08H_223 与重叠邻区崇贤北NF02H_141、陈家镇东NF02H_87；电子下倾 3°、垂直波束宽 6°、目标覆盖半径 500 m 等工参；逐日 MR 的采样点数（按窗口汇总后恰好复现原文覆盖率，逐日有波动）；实施后的后窗数据；现场实施与回填时间 2026-09-14 09:30／10:00；保护指标；崇明各乡镇的其他小区与庙镇新村NF02H_126；SHBAO 小区名称缺失（源工单只写“本小区”），名称按相邻小区宝泰支HR05H_111／_123 的命名规则补为宝泰支HR05H_112。

**两条假设**：A-S1——覆盖率＝RSRP≥-110 dBm 的采样占比，故弱覆盖占比＝1−覆盖率（原文只给覆盖率，待业务确认）；A-S2——崇明后窗覆盖率 91.36%（弱覆盖占比 8.64%）为构造，原文只写“指标恢复正常”。

种子里**不含“正确原因”标签**：原因全部由 F_08 从工参和 MR 计算得出。

**数据表**（`data/seed/`，表头即 SPEC 字段字典里的字段名）：

## 六、问答怎样工作

见 README“问答”一节。要点：不调用大模型；回答只引用函数结果、对象和 SPEC 元数据；每个数值日期都要能追溯到引用来源，测试逐条检查；优化本体只执行 A_01、A_02、A_04、A_07，其余动作只提示；假设演算（“如果 Y 的目标半径改成 560 米”“如果改电子下倾”）在内存中重算，不写入。

## 七、局限与待确认

- SPEC 的核心规则与测试假设本身待业务确认（SPEC 的未决事项 U01、U17～U19 等），本应用的判断同样保持“待确认”。
- 派单规则只有“一般场景”，VIP／VVIP 为规则缺口，按证据不足处理；规则文件没有写缺天处理与占比分母口径，按 SPEC 的 U17 拟定。
- 上海原工单的口径（覆盖率＜90%）与 SPEC 派单规则（弱覆盖占比≥20% 且采样点≥2000）不同，SHBAO 的差异是真实存在的，需要业务确认用哪个口径。
- SPEC 没有写透、本应用按以下方式理解的地方（均可在代码里一处改动）：①案例引用“须匹配适用条件”＝制式、站点类型、场景等级、区域场景、城乡、室内外、原因族逐项一致（厂家、下倾范围不比较）；②重叠邻区＝小区 `neighbors` 中 `overlapWeight`＞0 的邻区；邻区列表未提供时 F_10 记“未评估”；③保护指标：同天线小区取 MR 弱覆盖占比，重叠邻区取实测重叠覆盖度，已配置而后窗缺数据则效果待评估；④效果前窗取工单 `discovery.evidenceRefs` 所指的数据版本，后窗取最新版本；⑤“作用于 2 个及以上小区或 VIP／VVIP 追加优化主管批准”按 RULE_W14 原文实现。
- 4 张工单样本太少，只有崇明一张落在原因与处置范围内；这个应用验证的是 SPEC 模型的行为，不是现网效果。
