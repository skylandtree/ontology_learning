# 前端设计方案 —— 本体应用（上海工单）· 无线弱覆盖分析及优化决策工作台

版本：V2.4（2026-11-05）　适用实现：`本体应用_上海工单/web/`
对应后端契约：《本体与智能应用场景SPEC编制模板_弱覆盖_Day3_V0.9.md》§5.3「本体应用（上海工单）的前后端交互逻辑」
原型：`node web/server.js --port 27080` → http://localhost:27080/

> **V2.4 变更**：小区大屏收敛为**只列小区基础属性**（判定与处置不在大屏上给）；点开小区卡片后**自动执行决策链**（`POST /chain/run`），详情页首部新增**决策链执行状态条**，逐格显示七步的执行结果、委托标记、产出单据与判断时点推进记录。

## 一、设计定位

这套前端要在同一屏里同时说清三件事。任何一条设计决策如果不能服务其中之一，就不该做。

| 要一眼看出的 | 具体表现 | 反例（不要这样） |
|---|---|---|
| **这是本体应用** | 每条结论旁都挂着它依据的本体要素徽章（`F_08`／`INV_16`／`RULE_W06`／`OT_CELL_MR`），徽章可点开看定义、校验点与依据 | 只写"结论：命中"，不告诉人它由哪个函数、哪条规则得出 |
| **这是网优业务** | 逐日 MR 占比与派单门限、下倾几何剖面（挂高／波束宽／推荐下倾／缺口／rFar）、周边影响的远端半径与重叠指数、工单状态轨道、前后窗效果 | 把弱覆盖当成一条普通工单字段，用表格罗列布尔值 |
| **这是决策流程** | 详情页首部的**决策链执行状态条**逐格显示七步跑到哪、执行了什么、卡在哪；点进去是这条链的七步详情，每步标着"已完成／该做这一步／未开始／被阻塞" | 只有一排平铺的工单列表，看不出先后与依赖 |

三条轴的分工：

- **本体轴**回答「这个结论凭什么、约束在哪儿、被谁拒了」。
- **网优轴**回答「哪个小区、弱多少、调多少度、周边受不受影响、效果有没有持续」。
- **流程轴**回答「现在该做哪一步、做这一步需要谁点头」。

## 二、信息架构

### 2.1 流程起点是小区

需求把流程的起点从**工单**前移到**小区**：弱覆盖问题由前置数据（小区逐日 MR）按派单规则发现，工单是发现之后才出现的处置载体。因此前端只有一个一等的导航对象——小区。

```
┌───────────────────────────────────────────────────────────────────────────┐
│ 顶栏  品牌 │ 面包屑：小区大屏 / 崇贤达NF02H_222 │ 本体遥测 │ 时点 │ 角色 │
├────────────┬────────────────────────────────────────────┬─────────────────┤
│ 左轨        │ 主工作区                                    │ 右栏            │
│ ① 小区      │  小区大屏（卡片墙）                          │ ① 本体要素检查器 │
│    大屏      │        或                                  │ ② 本体问答      │
│ ② 当前小区  │  决策链执行：过程状态 + 执行结果本体图谱     │   （带当前小区  │
│    · 决策链  │    （步骤详情点卡片后弹窗，不占主视图）       │     上下文条）   │
│ ③ 本体      │        或                                  │                 │
│    驾驶舱／  │  本体驾驶舱／本体图谱／案例库                 │                 │
│    图谱／案例│                                             │                 │
├────────────┴────────────────────────────────────────────┴─────────────────┤
│ 状态栏  服务在线 │ 小区/工单/方案/效果/案例/MR 计数 │ 最近动作 │ traceId      │
└───────────────────────────────────────────────────────────────────────────┘
```

左轨**不平铺七步**：小区是唯一的一等对象，点开小区后左轨只留"当前小区 + 决策链执行"一个入口；七步在决策链里，点哪张卡片看哪一步。

三栏固定（232px / 自适应 / 372px），顶栏 56px、状态栏 28px 固定。`body{overflow:hidden}`，只有主工作区与右栏各自滚动——仪表盘不该整页滚动。

### 2.2 两个页面

| 页面 | 回答的问题 | 进入方式 |
|---|---|---|
| **小区大屏** | 有哪些小区、各自的基本属性是什么？ | 启动默认页 |
| **决策链执行（小区详情）** | 这条链跑到哪一步、这一步执行了什么、结果牵出了哪些对象？ | 点小区卡片（自动执行决策链） |
| **步骤详情弹窗** | 第 N 步的推理过程是什么、这一步的结果是什么？ | 点决策链上的第 N 张步骤卡片 |

大屏**只列小区基础属性**，不做判定。理由：判定是决策链跑出来的结果，放在大屏上就变成"看板替人做判断"，而且一旦大屏上有了判定三态，用户就会在大屏上挑"命中的小区"而不是让链自己走。基础属性（制式、频段、站点类型、场景等级、区域、目标半径、发射功率、重叠邻区）足以定位与筛选，判定与处置一律留到详情页。

### 2.3 小区详情的 7 步决策流程

| # | 步骤 | 回答的业务问题 | 主要本体要素 |
|---|---|---|---|
| ① | 发现与判定 | 这个小区为什么（不）算弱覆盖？缺什么？ | `F_12`／`F_06`／`F_05`、`OT_CELL_MR`、`RULE_D01~D04` |
| ② | 工单与定因 | 工单为什么存在、现在到哪一步、根因是什么？ | `A_01`～`A_03`、`F_07`／`F_08`、`OT_TICKET` |
| ③ | 优化方案 | 调多少度？分几轮？周边会不会受影响？ | `F_09`／`F_10`、`A_04`、`OT_PLAN` |
| ④ | 确认派单 | 能不能批？谁必须批？ | `A_05`、`INV_05`／`INV_06`、`RULE_W14` |
| ⑤ | 实施回填 | 现场实际调了多少？和计划一致吗？ | `A_06`、`OT_ANTENNA`、`INV_07`／`INV_15` |
| ⑥ | 效果核验 | 改善了吗？达标了吗？持续有效吗？ | `F_11`、`A_07`、`OT_EFFECT`、`TH09~TH13` |
| ⑦ | 闭环与案例 | 能不能关单？案例能不能复用？ | `A_08`／`A_09`、`OT_CASE`、`RT_15` |

每一步在决策链状态条上带一个状态：**● 已完成**（绿）／**◐ 执行中**（青，呼吸）／**○ 未开始**（灰）／**◆ 被阻塞**（琥珀：草案、冲突、证据不足）。状态取后端链的返回值（与卡片下方摘要同一份事实），前端不自己判断流程走到哪儿；步骤本身不再作为左侧固定入口，点卡片才打开弹窗。

### 2.2b 决策链：自主执行与执行状态条

**进入小区详情即自动执行决策链**（`POST /chain/run`，体 `{ cellKey, until }`）。链在后端按本体推进：每一步走本体自己的动作入口，能走到哪一步走到哪一步。前端不参与推进，只负责把结果摆出来。

**小区详情只有两块内容**：①决策链过程状态（状态条＋七步卡片＋已产出单据＋摘要）②这次执行结果的本体图谱（`GET /trace/cell` 的 `lineage`，`viz.ontologyLineage` 画对象—关系）。**七步正文不在主视图平铺**：点任意步骤卡片弹出「步骤详情」，上半是那一步的**本体推理过程**（该步真正调用到的 `F／A／INV／RULE／TH` 与结果），下半是那一步的**结果**（原来的步骤正文，含动作按钮）。弹窗动作执行完、流程往前走时，主视图仍停在决策链，弹窗自动切到下一步，状态条由静默同步刷新（`chainTarget`＝刚做完的那一步，不再往下自动推进）。

**按步执行、逐步呈现。** 前端不是等整条链跑完再一次性刷出七格，而是一步一调：`until=1` 拿到第 ① 步的真实结果并摆出来，接着 `until=2`……每一步的结果出来后才走下一步。体里的 `until` 让后端只执行到第几步（1～7），返回 `outcome: "partial"` 与 `nextStep`；七步走完返回 `completed`，走不通返回 `stopped` 并带上止步的那一步与原因。前端给正在执行的那一格加青边呼吸与「执行中」标记——**执行一步、出一个结果**，看得见进度，而不是一个转圈之后突然全部完成。走不通时停在那一格，后面几格标「未执行」，当前结果（已产出的工单／方案／派单／效果／案例）保留在条上。条头另有「跳至结果」，点了就不再逐步展示，一次跑到结果。

**每步 2～5 秒，主视图只摊一行"最近调用"。** 两步之间不是固定短停顿，而是每步随机 **2000～5000ms**（`CHAIN_STEP_MIN`／`CHAIN_STEP_MAX`）。状态条正下方是一条**折叠态**的「本体推理过程」：平时只显示最后一条调用（如 `INV_14 同一小区…不重复建单 ✓`）＋「已记录 N 条 · 点步骤卡片看完整过程」，执行中随调用滚动替换，**不把单步的过程铺在主视图上**。完整过程只在步骤弹窗里：`RULE_F01` → `F_12 批量发现（命中 3/7 天）` → `OT_CELL_MR 7 条日统计` → `INV_01／INV_09／INV_16 校验` → `A_01 建单 TK-…-001`，第 ⑤、⑥ 步还有「判断时点推进」与「现场回填记录到达」；那一步还在跑时，弹窗打开后会跟着现场记录一条条长。来源是运行期 `tracker.tap` 旁听到的 `INV／RULE／TH` 实际调用＋链自己记的动作结果（`step.trace`），**不是前端编的过程**：要素名取本体定义，编号不可自造，动作行以结果收尾。

```
┌─ 决策链执行状态 ─ AUTONOMOUS CHAIN ── [◌ 执行中 4/7 · 第 5 步「实施回填」] ─ 09-11 → 09-17 [跳至结果] ─┐
├ 本体推理过程 ─ ONTOLOGY CALLS ──────────────── 已记录 23 条 · 点步骤卡片看完整过程 ──┤
│ 5  来源事实 现场回填记录 SHCHM0112… 机械下倾角 4.0°→5.0°（回执 成功）                  ✓ │
├──────────────────────────────────────────────────────────────────────────────────────────────┤
│ ①发现与判定 ✓ │ ②工单与定因 ✓ │ ③优化方案 ✓ │ ④确认派单 ✓ │ ⑤实施回填 ◐执行中 │ ⑥效果核验 ○ │ ⑦闭环与案例 ○ │
└──────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**详情页首部的「决策链执行状态」条**是这个页面的第一件事（在步骤标题之上），它回答四个问题：

1. **跑到哪一步**——七格一排，每格一格标已完成／受阻／未执行，卡住的那格标红并给出原因；
2. **执行了什么**——每格下面列出执行过的动作（`A_01`…）+ 执行身份 + 结果；SPEC 要求人工确认而由链委托执行的步骤带「委托」徽章；
3. **卡在哪、为什么**——底部一条红框：止步于第几步、哪条约束、缺什么；
4. **产出了什么**——工单／方案／派单／效果／案例的单号，以及判断时点的推进记录（推进到什么时候、为什么推进）。

```
┌─ 决策链执行状态 ─ AUTONOMOUS CHAIN ─────── [已走通 7/7] ─ 09-11 → 09-29 [重跑] ─┐
│ ①发现与判定 ✓ │ ②工单与定因 ✓ │ ③优化方案 ✓ │ ④确认派单 ✓ │ ⑤实施回填 ✓ │ ⑥效果核验 ✓ │ ⑦闭环与案例 ✓ │
│ A_01 优化本体 成功 │ A_03 地市优化工程师 委托 成功 │ …                              │
│ 工单 TK-…  方案 PL-…  派单 DP-…  效果 EF-…  案例 CS-…                               │
│ 判断时点推进 3 次：等现场回填记录到达 / 后窗需满 7 天 / 持续有效需满 14 天          │
└──────────────────────────────────────────────────────────────────────────────────┘
```

**为什么委托要写在界面上。** SPEC §自动与人工边界把 A_03／A_05／A_08／A_09 定为"须人工确认"。链以本体动作表允许的角色代为执行，是一次**委托**，不是一次自动授权——所以它必须显眼：徽章（委托）、审计里的执行身份与角色、以及 `delegate:false` 时链停在等人。复核者一眼能看出哪几步不是"自动"跑完的。

**停住时给人工接入入口，但不暗示"再等等就能过"。** 执行中的停点只有两类（`stop.cause`）：`cannot-infer` 本体推不出（缺事实／证据不足／冲突不能裁决／模型不成立）、`expectation-unmet` 结果不满足期望（`F_10` 不通过、持续有效不成立）；发现阶段就不成立或状态不允许是终态，不给入口。链停在“人手里那条事实／那个决定”还缺着的步骤时，止步提示下面多一块**人工接入处理**（`cellflow.humanBlock`）：本体依据（`stop.code` ＋ `stop.basis` 约束原文）→ 期望与缺口（`stop.expected`／`stop.gap`）→ 推理结论（`stop.reason`，第 N 步之后不执行）→ 需要人工（`stop.human.role`／`what`／`then`）→ 处理入口。缺现场实际值时给出回报表单（实际值／实施时间／回执／执行方 → 「现场回报并继续执行」，`POST /facts/field-executions`，只补来源事实、身份按 A_06 角色校验），处理完也可以直接「处理后继续执行」重跑同一条链（幂等，停点之前的步骤静默重放）。**没有 `stop.human` 的停点（规则缺口、证据不足、未达到、已排除、终态）不显示这块**——那些是真结论，不是等人。演示小区：陈家镇北NF02H_196（①②③④走完后停在 ⑤，本体推不出 F_11 的结论，回报后走完 ⑥⑦）。它的 MR 故事固定在 2026-09-04～09-28、起点判断时点 2026-09-11 09:00；判断时点被别的小区推走后，发现窗口会落到故事之外、第一步判“未达到”。大屏提示与第一步止步提示都给了「从 09-11 重演」——重建运行时（`/__reset`）再打开该小区，不是把时钟偷偷拨回去。

**时点自己往前推。** 等现场回填记录、凑够效果后窗，都是时点问题。链把判断时点推到本体算出的最早可评估时刻（参数 `effectMinDaysAfter`／`effectSustainDays` 与派单规则的窗口天数），每次推进都记下时点与原因。推进是全局的，所以链跑完后前端要重新读一次服务端时钟，再刷新当前小区上下文。

### 2.4 前端持有的状态

| 状态 | 作用域 | 影响 |
|---|---|---|
| 当前角色 | 全局 | 全部请求的 `x-context-key-groups`；决定动作按钮可用性与文案 |
| 判断时点 `asOf` | 全局 | 所有读请求的 `asOf`、函数请求的 `refTime`；以服务端时钟为准（链推进后要重读） |
| **当前小区 `cellKey`** | 全局 | 详情页的全部对象与动作入参；问答的上下文（相对指代） |
| 当前工单／方案／效果 | 随小区 | 对象查询主键、关系读取（`/objects/{type}/{id}/relations`）的起点、动作入参 |
| **决策链结果 `chain`** | 随小区 | `POST /chain/run` 的返回：七步状态、动作、产出单据、止步原因、时点推进记录；首部状态条直接渲染它 |
| 决策链展示进度 | 随小区 | `chainReveal`（已显示到第几步）／`chainPulse`（正在执行第几步）／`chainRun`（按步循环在跑）／`chainTrace`（现场调用记录，主视图只显示最后一条）／`stepTraces`（各步全量记录，只在弹窗里展示）；只影响显示节奏，不影响任何请求与判定 |
| 步骤弹窗 `modal` | 随小区 | 1～7＝打开该步的推理过程与结果，`null`＝关闭；`Esc`／点遮罩／「关闭」都可收起 |
| 流程同步 | 随小区 | `chainStale`（动作推进后待同步到第几步）／`chainTarget`（这次只跑到第几步）／`chainFast`（静默跑，不放动画） |
| 小区基础属性表 `board` | 全量小区 | `cellKey → {siteType, areaName, antennaId, …}`；大屏卡片的数据源（来自 `OT_CELL`＋RT_01／RT_02／RT_04，不做判定） |
| 筛选与搜索 | 会话 | 大屏卡片的过滤条件（制式／场景等级／站点类型／关键字） |

## 四、核心组件

### 4.1 小区卡片（大屏）

一张卡片回答"这是哪个小区、它的基本属性是什么"——**只摆属性，不摆判定**：

```
┌崇贤达NF02H_222───────────────────── [LTE] ┐
│ LTE:156514014                              │
│ [B3][宏站][一般][乡镇道路]                  │
│ 目标半径 500 m      发射功率 12.2 dBm       │
│ 区域 陈家镇陈东路周边  重叠邻区 2 个        │
│ 611382-2-1  611382      点开自动执行决策链 → │
│ [OT_CELL]                                   │
└─────────────────────────────────────────────┘
```

- 卡面上的字段全部来自本体对象与其关系（`OT_CELL` ＋ RT_01→站点、RT_02→天线、RT_04→区域），**没有一行是判定**。
- 缺数据写"未提供／未关联／未知"，不写"—"、不写 0：本体里没给邻区是"未知"，不等于"没有邻区"（SPEC：`neighbors` 未提供＝未知）。
- 底部一行提示"点开自动执行决策链 →"，把大屏与详情页的关系说清楚。
- KPI 改为属性分布（小区总数／LTE／NR／宏站／室分），筛选器也只按属性筛（制式／场景等级／站点类型／关键字）。

**为什么大屏不摆判定。** 判定是决策链跑出来的结果，摆在大屏上会让人以为"看板替人做了判断"，也会诱导用户在大屏上挑"命中的小区"再点进去，而不是让链自己对每个小区走一遍。基础属性足以定位与筛选；跑不到哪一步由本体说了算，写在详情页首部。

### 4.1b 决策链执行状态条（详情页首部）

见 §2.2b 的信息设计。视觉规则：

| 元素 | 样式 | 含义 |
|---|---|---|
| 格顶色条 | 绿／红／灰 | 该步已完成／受阻／未执行 |
| 状态字 | `已完成`／`受阻`／`未执行`／`未开始` | 链的执行状态（后端给的原值） |
| 动作行 | `A_05` 徽章＋执行身份＋结果徽章 | 链执行过的动作；结果为"成功"绿、"拒绝"红、"待人工"琥珀 |
| 「委托」徽章 | 琥珀 | 该动作 SPEC 要求人工确认，由链以动作表允许的角色代为执行 |

## 六、交互原则

### 6.0 决策链自己往前跑

**点开小区＝自动执行决策链。** 不再要求用户逐步点按钮把流程推完：进入小区详情时前端自动按步调 `POST /chain/run`（`until=1`、`2`……），链在后端按本体推进，能走到哪一步走到哪一步；每一步的结果先摆上状态条，再走下一步。

这不是"把按钮自动点一遍"，规则有三条：

1. **链不绕过本体。** 每一步都走本体的动作入口（角色校验、INV 约束、审计留痕照旧）。链能做的只是把"走下一步"这件事自动化，不是给自己开权限——本体的约束说不行，链就停在那一步。
2. **委托要写在界面上。** SPEC 要求人工确认的四步（A_03／A_05／A_08／A_09）由链以动作表允许的角色代为执行，界面标「委托」徽章、审计记执行身份与角色。`delegate:false` 时链停在这些步骤前等人——两种口径都能看到。
3. **停在哪儿要能解释。** 状态条给出一句话：止步于第几步、哪条约束、缺什么（"判定「证据不足」：规则缺口：…"、"无现场回填记录：现场未回报…（INV_07）"）。只说"失败"没有用。

**为什么不让用户自己一步步点。** 原来每一步都要点按钮，等于让人替系统做调度：人得记住现在到哪一步、该点哪个按钮、必填参数是什么。链自己走之后，人的位置从"调度器"变成"复核者"——看结果、看依据、在链停住的地方接手（链停在须人工确认的步骤时，那一步的按钮就是接手的入口）。

**手动入口还在。** 七步的动作按钮全部保留：链跑到某步停下（须人工确认、缺现场回报、周边影响不通过），人可以在详情页接手处理，处理完点「重跑」或「处理后继续执行」让链接着往下走。缺现场实际值／工参待裁定这类“补一条事实就能继续”的停点，止步提示下面直接给**人工接入处理**块（见 2.2b）——链不拿计划值冒充现场值，也不越过人替现场签字。

### 6.1 流程只靠点击推进

决策流程的每一步，动作的必填参数都由界面上已有的证据自动推导出来，并显示在界面上；用户不填任何字段也能往下走。

| 步 | 必填参数 | 从哪来 |
|---|---|---|
| ② A_03 确认／排除 | `reason` | F_07 的重合判定、F_08 的命中与缺口、并列次因、已写入的主因标签——汇总成一句可审计的复核判断 |
| ④ A_05 批准并派单 | `approvals[]`、`reason` | 审批链＝发起角色＋（影响范围 ≥2 个小区或 VIP／VVIP 时）优化主管，与 A_05 的判定同口径；理由＝可批准性结论＋影响范围＋RULE_W14 |
| ⑤ A_06 回填 | `executeTime`、`receipt`、`actualValues[]` | 现场回填记录（`GET /facts/field-executions?cell=`）——任务号、实施时间、收到时间、执行班组、回执、前值→后值；`dispatchNo` 取自方案的 `execution` |

三条配套规则：

1. **推导出来的值可见、可改。** 字段里是推导值，标注"已按…自动生成，可改"；改过的以用户为准（`state.overrides`），换小区即作废。表单只是"改一下"的入口，不是"填一下才能走"的前置。
2. **点击前看得见要写什么。** 每个动作按钮旁一行"本步提交：…"的参数摘要，让人在点之前就知道这次会写什么。
3. **没有来源事实就不给假值。** 现场回填记录按 `receivedAt` 到达：没到时"回填"按钮置灰并说明"尚无现场回填记录…不得用计划值代替实际值（INV_07）"，另给一个"A_06 记回执缺失（未知）"的按钮——这正是 `INV_08` 要求的路径（工单留在处置中，不得评估或关闭）。**不用计划值冒充实际值**。

### 6.2 定因一步到位，动作后自动进下一步

② 工单与定因原本要用户做三件事：点"执行 F_07"、点"执行 F_08"、往"复核判断"里写一句话再点确认。现在：

- **依据自动取回。** 载入小区时界面自己调 F_07／F_08 并缓存（按工单号＋判断时点失效），"假性弱覆盖""下倾角命中"两块面板一直有内容；写入根因后改用工单自己的诊断记录（权威）。原来那两个"执行"按钮收成一个"重新计算"。
- **裁决依据只读展示。** 自动汇总的那句判断以普通文字呈现（`裁决依据 AUTO · 可改`），要改才点"改写"露出输入框。**必填输入框不再挡在"下一步"前面**。
- **一个按钮完成定因。** `写主因并确认（A_02 → A_03）` 连续执行两个动作：A_02 按规则写主因 → 读回工单 → 用最新证据生成复核判断 → A_03 确认。规则定因不成立时（A_02 未写入）停下来并说清原因（F_07＝排除 ⇒ 该走"排除"；F_08 未命中 ⇒ 需人工定因或转专家），不给死路。
- **动作后自动进下一步。** 定因确认→优化方案；生成方案→确认派单；派单→实施回填；回填→效果核验；关单→闭环与案例。弹窗自动切到下一步，决策链状态条静默同步刷新，用户不必回导航里找下一步。

### 6.3 角色不先试后错

按钮的可用性由 `/actions` 元数据里的"允许角色"决定：当前角色不在允许列表 → 按钮置灰 + 悬停说明"当前角色『X』无权执行 A_04（允许：优化本体）"+ 按钮旁常驻小字"A_04 需 优化本体"。

真实业务里这条尤其重要：`A_04` 只有优化本体能执行，`A_08` 只有优化主管，`A_09` 只有专家／知识维护人。所以一次完整闭环需要切换四次角色——这正是真实协同的样子，界面要把这件事讲明白。

**但不该让人卡在"先切角色、再点回来"。** 当动作的状态前置条件已经满足、只是当前角色无权时，按钮旁多一个**「以 优化本体 执行」**的小按钮：一点就切到本体允许的角色并立即执行这一步（`state.role` 与请求头 `x-context-key-groups` 同步改）。这不是代办——动作仍由本体按角色校验、留审计；只是把"换班"和"干活"合成一次点击。状态前置不满足时不出现这个按钮（换了角色也做不了，给了就是骗人）。

### 6.4 判断时点是一等状态

顶栏的时钟输入框直接可编辑，回车即推进本体仿真时钟（`POST /sim/clock`）。改时点＝全量重发读请求，且**以服务端时钟为准回读**（推进后详情页的发现窗口、卡片的判定随之切换）。决策链自己推进时点也是同一套机制：链跑完前端重新读一次服务端时钟，再刷新当前小区上下文。

推时点会释放按 `receivedAt` 陆续到达的 MR 数据——这让"数据还没到"和"数据到了但不合格"在界面上可分辨。

**可执行时点也由界面指出来。** 有些步骤不是"随时可做"，而是"等到某个时刻才成立"：⑤ 等现场回填记录到达（后端给的 `receivedAt`），⑥ 等后窗攒够 MR 天数（本体参数 `effectMinDaysAfter`／`effectSustainDays` ＋ 派单规则窗口天数）。这些地方各给一个**「推进到 …」**按钮，一键把判断时点推到那个时刻（时点是界面给的，判定仍由后端给——推早了，后端照旧判"待评估"）。

推时点的日期由本体参数算（`GET /definition` 的 `params`），不是前端拍脑袋；MR 次日凌晨才入库，所以留足一天。

### 6.5 未知是一等公民

- 全局三态样式（4.3）。
- 不用灰色小字把"未知"藏起来；缺数据的格子画斜纹。
- `F_08`＝未知时**不画几何图**；`F_11`＝待评估时保护指标区显示"未评定"而不是空表。

### 6.6 拒绝即证据

后端拒绝（`INV_xx`／`PERMISSION_DENIED`／`REVIEW_REQUIRED`／`STALE_FACTS`／`ROUND_IN_PROGRESS`／`SUPERVISOR_REQUIRED`）不弹一句"操作失败"了事。提示卡给出：

```
PERMISSION_DENIED · a04-mech
角色"地市优化工程师"无权执行 A_04（SPEC 允许：优化本体）
当前角色无权执行该动作
trace e1eaab09c6b03e413
```

约束拒绝额外给出该 `INV_xx` 的语义与可执行的下一步（补证据／改时点／转人工），而不是让用户猜。

拒绝同样留审计——动作反馈里的 `audit.runId` 直通 `GET /audit/runs`。

### 6.7 问答针对当前小区，且只读

问答面板顶部固定一条上下文条：**当前小区**（小区名＋cellKey，没有选中小区时写明"未选小区（全局问答）"）。问题里的"它／这个小区／该小区"因此有确定指向——相对指代由后端按 `cellKey` 解析（`src/qa.js`），前端不猜。

问答**只回答不做**：即使本体授权优化本体自动执行 A_01／A_02／A_04／A_07，问答面板也只提示"到决策流程的第几步点按钮执行"，不产生写入与审计。写操作一律在小区决策流程页完成——决策页负责写，问答页负责问。

回答页脚只标**事实是否可追溯**，不标"这一段文字由谁生成"：

| 状态 | 标注 | 颜色 |
|---|---|---|
| 数值全部可追溯到本次引用的来源 | `落地 ✓` | 灰 |
| 有数值/编号未落地 | `落地 ✗` | 琥珀 |
| 未做落地检查 | `落地 —` | 灰 |

**不暴露实现层**：问答面板不出现"语义理解：规则／大模型"的切换，也不出现"模型未启用 · 已用规则回答""LLM · 模型名"这类标注。语义理解与措辞用哪种引擎由后端配置（`config/llm.config.json` 的 `semantic_engine`）决定，前端不感知、不展示；引擎不可用时后端静默退回规则，回答口径与规则模式完全一致，用户看到的只有本体事实。

### 6.7b 问答面板：引子、推荐提问、流式输出、依据本体资源

**引子**（面板顶部，一句话）：说明"我是谁、能问什么、回答依据什么"——

> 我是当前小区的问答助手：可以问我这个小区有哪些属性、它已经走完的决策全流程是什么、某个结论依据本体里的哪些对象与函数——回答只引用本体里的事实，每个数值都能追溯到出处。

**推荐提问**（面板底部，输入框上方）：点一下只是把问句**填进输入框**并聚焦，由用户回车或点"发送"发起提问——不自动提交，避免误发。题目随上下文变：

| 上下文 | 推荐提问 |
|---|---|
| 有当前小区 | `<小区名> 的基本信息`／`<小区名> 已经完成的决策全流程`／`<小区名> 的根因是哪一类问题`／`<小区名> 的工单状态怎么样`／`<小区名> 的效果怎么样`／`哪些小区弱覆盖` |
| 无当前小区 | `哪些小区弱覆盖`／`派单规则是什么`／`工单有哪些状态`／`F_08 是什么`／`INV_16 约束什么` |

**流式输出**（`POST .../qa/ask/stream`，SSE）。帧序：`meta`（引擎／阶段）→ `refs`（回答依据的本体资源）→ `delta`（增量文本，逐句）→ `done`（完整回答＋落地检查＋写入与待人工动作）。前端收到 `delta` 就追加到当前消息并重画（70ms 节流，只重画右栏，不重画整页），回答末尾留一个闪烁光标表示还在送出；`meta` 帧带阶段，回答还没出头一个字时先显示"正在理解问题／正在读取本体事实／正在组织语言"，不让用户对着空白等。

**首字不等整段生成完**：后端把网关的增量接到一句就送一句（按句读切，长句退到逗号切），不攒完整段再回。语义理解也不再固定整轮先跑：规则引擎在本进程内先认一次意图（毫秒级），认出来就直接取事实、只调一次模型做措辞；只有规则接不住的口语问法才调语义解析。本体外补充段与正文改写并发取回，谁先好谁先到。

**依据本体资源**：每条回答下方一行"依据本体资源"，列出本次回答引用的本体要素徽章（`OT_`／`RT_`／`F_`／`A_`／`INV_`／`RULE_`／`TH`），按要素类型分色，点徽章进右栏检查器。`refs` 帧一到就先显示，读者在文字还没送完时就知道它依据什么。

**数值落地检查在送出之前做**：大模型改写出的句子先过落地检查，通过才送出——逐句校验、逐句送出，未校验的句子一句都不往外送。某句出现事实里没有的数字或单号，立刻停手重写一次；重写仍不过就用 `replace` 帧整段换成规则原文——界面不会留下半句没校验过的话。

**"已经完成的决策全流程"是新问法**：规则引擎按本体执行链路逐步讲（每步的动作、执行角色、成功还是被哪条约束拒绝、关键数值、依据的函数），与「决策链执行」里每步的推理过程同源。

## 九、已知限制

1. **视角**：大屏只到小区维度，没有"全量在办工单"的独立看板（`POST /objects/OT_TICKET/query` 已能支持，待加）。
2. **扇区态势图**：目前只画受影响小区集合，没有叠加完整的路网底图与全部邻区权重。
3. **问答**：规则模式覆盖 58 个意图，换一种问法可能识别不出；后端把语义理解切到大模型后由模型解析，但模型不可用时仍退回规则，且事实始终来自本体函数、数值未落地自动回退规则原文；页面不体现引擎差异。
4. **时点回放**：接口层支持 `asOf`，前端目前只用于统一读时点，没有做成可拖拽的时间轴回放。
5. **数据边界**：MR、工参、告警、派单均为本地仿真种子，不代表现网；SPEC 的核心规则与测试假设本身尚待业务确认，界面结论一律保持"待确认"。
6. **决策链会推进全局时钟**：链为等现场回填记录、凑效果后窗会把判断时点往前推，这是全局的——在链跑完之前看过的小区，回到大屏再点会落在新的窗口上。若要复现某一步，把时点拨回去再点「重跑」。
7. **链的委托口径写在报告里**：A_03／A_05／A_08／A_09 由链以动作表允许的角色代为执行（SPEC 要求人工确认）。界面标「委托」、审计记执行身份与角色；接真实业务时，这几步要么关掉委托（`delegate:false`）由人确认，要么把链的执行边界与审批流程重新谈一遍——这一层目前只在技术口径上落定，业务授权尚未确认。
8. **主线小区闭环后不再命中派单条件**：崇贤达 NF02H_222 处置完成（2026-09-14 起）后逐日 MR 恢复到 8.64%，`F_12` 随即判"未达到派单条件"——这是判定本身的结果，不是数据缺失。链重跑时也据此复述"已执行完毕"，不会重复开单。
