# ontology_learning

面向无线弱覆盖优化的本体学习与应用项目，包含本体建模、业务规则与函数、受控动作、七步处置流程和可选的大模型问答。

需要 Node.js ≥ 22.13，无第三方运行依赖，无需 `npm install`。在项目目录执行：

```bash
npm start       # 启动页面：http://127.0.0.1:27080/
npm test        # 运行本体、业务接口和 Web 回归测试
```

默认无需模型密钥即可按规则运行。启用模型问答时，将 `config/llm.config.example.json` 复制为 `config/llm.config.json` 并填写本机配置；真实配置、密钥、数据库、日志和录屏产物不提交到仓库。

## 上海覆盖工单：基于 SPEC 的本体决策与问答应用

按《本体与智能应用场景SPEC编制模板_弱覆盖_Day3_V0.9.md》（下称 SPEC，副本在 `spec/`）实现的本地应用，用上海 4 张真实优化工单（`data/副本上海工单.xlsx`）的事实作样例：

- **本体只来自 SPEC。** 对象类型、属性、关系、函数、动作、约束、规则、测试假设、派单规则、措施类型字典，全部由 `scripts/gen-ontology.js` 从 SPEC 的表格解析生成（`ontology/shwo.ontology.json`），运行期不读任何其他定义。写入 SPEC 没有定义的对象类型、属性、关系，一律被拒绝。
- **决策场景与问答场景覆盖 SPEC 定义的全部本体要素。** 9 个对象类型、17 个关系、12 个函数、11 个动作、17 条约束、19 条规则、12 项测试假设，每一个都在场景里被实际用到；覆盖矩阵见 `reports/coverage-matrix.md`，由测试自动生成并断言。
- **从前置数据发现问题，而不是从工单出发。** 小区逐日 MR（`OT_CELL_MR`）是锚点；`F_12` 按派单规则只读地发现弱覆盖小区，`A_01` 重算后才建单，工单只是下游处置载体。
- **前端的流程起点也是小区。** 大屏只列**小区基础属性**（制式、频段、站点类型、场景等级、区域、目标半径、发射功率、重叠邻区）——属性全部取自本体对象与其关系，大屏不做判定。点卡片进入该小区，**决策链自动执行**：从发现判定一路跑到闭环与案例，**能走到哪一步就走到哪一步**（走不动的地方就是本体约束挡住的地方，界面写清是哪一步、哪条约束、缺什么）。详情页只有两块：**决策链过程状态**（七格显示完成／受阻／未执行，每格列出执行过的动作，另有产出的工单／方案／派单／效果／案例与时点推进记录）和**这次执行结果的本体图谱**（对象实例与 RT 关系）。**七步不作为左侧固定入口**：左轨只有"当前小区 · 决策链执行"，点任意步骤卡片才弹出该步的**推理过程＋结果**。
- **自主执行不越过本体的治理边界。** 链的每一步都走本体自己的动作入口（`app.act`）：角色校验、INV 约束、审计留痕一律照旧，链不绕过任何一条；SPEC 要求人工确认的步骤（A_03 确认／排除、A_05 确认并派单、A_08 关闭、A_09 入库）以本体动作表允许的角色**委托执行**，报告里标「委托」、审计里记执行身份与角色，复核者一眼能看出哪几步是委托来的。天馈类措施一律派给现场维护人员执行，不由链自动执行（INV_05）。
- **本体图谱看得懂“本体长什么样”。** 左轨「本体图谱」直接展示**整个构建好的本体**：9 个对象类型与 17 类关系（19 条端点关系）一张图摊开，连线标注 RT 编号与方向，自环表示同类型关系（RT_03 邻区、RT_07 复发），派生关系用虚线；下方是关系类型表、对象类型表与要素清单。图与表全部取自 `GET /definition`，**不随当前小区或判断时点变化**；某个小区实际跑过的流程与实例谱系在「决策链执行」（对象谱系来自 `GET /trace/cell`）。
- **决策流程只靠点击推进。** 动作的必填参数不要求用户手填，一律由界面上的证据自动推导并显示出来：复核判断来自 F_07／F_08 的判定与诊断、审批链来自影响范围与场景等级、回填的实施时间／回执／现场实际值来自现场回填记录（`GET /facts/field-executions`）；每个动作按钮旁给出"本步提交"的参数摘要，推导出来的值可以改，改了以用户为准。**角色门禁也不卡人**：状态已满足、只是当前角色无权时，按钮旁多一个「以 优化本体 执行」／「以 优化主管 执行」的小按钮，一点换身份并执行；**等数据的步骤也不卡人**：现场回填记录没到、后窗天数没攒够时，按钮旁直接给「推进到 2026-09-14 10:00」「推进到最早可评估时点」——时点由后端事实与本体参数算出来，判定仍由后端给。这些按钮都在**步骤弹窗**里（点卡片打开），执行完弹窗自动切到下一步、状态条静默刷新。
- **定因一步到位，动作后自动进下一步。** F_07／F_08 的依据由界面自动取回（不必先点"执行"）；"写主因并确认"一次点击完成 A_02 与 A_03，裁决依据以只读文字展示（要改才点"改写"）；确认定因后弹窗自动切到优化方案，后续每一步动作成功后同样自动进入下一步——不必回导航里找下一步。

- **种子数据是 CSV，一张表一个文件，看起来就是真实的网管数据。** 站点用 eNB／gNB ID、小区用 ECI／NCI 标识（LTE 的 ECI＝eNB ID×256＋小区号）、天线编号是“站点-扇区-序号”，MR 日统计的采样点数逐日波动并在业务日次日凌晨陆续到达（时钟推进到哪天，数据才入库）。九月的 11 个上报小区**逐日连续上报 09-04 ~ 09-28**，日型由首周实际取值反推后按周重复——任何 7 天窗口的判定都与首周一致，时钟往前推，小区不会一夜之间全变成“数据缺口”。决策场景和问答都在这份数据上执行，输出里只有真实风格的小区名与编号。哪些是原文、哪些是按格式补齐的，只记在 `data/seed/provenance.csv`，被问到时才回答。

当前状态：**本地仿真**（Node.js 内置 SQLite，零第三方依赖），未接入 MR 平台、资源库、告警或派单系统。补齐的数据不代表现网。

## 快速开始

### 0.4：云端响应优化与独立分析

前端默认使用“独立分析”：每次点击小区都从种子数据与 `2026-09-11 09:00`
开始，时钟、工参、工单、案例、审计和问答状态不会被上一次分析或其他访问者影响，
无需先点“重置”。“重置”只作用于当前分析。需要跨小区保留本轮时点、工单和案例时，
可选择“连续分析”；原有连续处置与案例复用能力仍保留。

默认“快速结果”直接执行原七步决策链并展示真实结果，所有步骤的推理记录仍可点开。
“逐步演示”保留原有每步展示节奏及“跳至结果”入口，两种方式使用同一套业务规则。

初始化和详情通过应用层只读聚合接口读取；每个聚合读取仍调用原 OSDK 接口，
函数、动作、约束、权限与业务规则没有变更。菜单先渲染，统计与审计在后台更新。
各分析使用独立内存运行时，服务重启后回到种子数据；空闲分析一小时后可回收，
关闭页面或开始新一轮时会释放不再使用的分析。原 OSDK 不带分析标识的调用方式保持兼容。

```bash
node test/llm.js                # 本地假网关验证模型编排、SSE 和回退，不调用真实网关
```

## 自主决策链：点开小区就跑完能跑的那一段

`POST .../chain/run`（体 `{ cellKey }`）把一个小区从**发现与判定**一路推到**闭环与案例**，能走到哪一步走到哪一步。前端在点开小区卡片时自动调用它，详情页首部的**决策链执行状态**条就是它的返回。

**按步执行与逐步展示。** 体里加 `until: 1..7` 时，这一次调用只执行到第 `until` 步，剩下的步骤返回 `status: "pending"`，报告 `outcome: "partial"` 并给出 `nextStep`。前端据此一步一调（`until=1`、`2`……）、一步一显：每步的结果出来后才走下一步，走不通就停在那一格并标出后续「未执行」，而不是等整条链跑完再一次性刷出七格。带 `until` 与不带 `until` 的最终结论一致（同一张工单、同一个案例、同样两条效果记录），测试第 14 组逐项断言。

**推理过程与节奏。** 每步之间停 **2～5 秒**（`CHAIN_STEP_MIN/MAX`，随机）。这段时间里主视图**只留一行**「最近一次本体调用」——`INV_14 同一小区…不重复建单 ✓` 这样一行，随执行滚动替换，证明链确实在一层层调本体；**单步的完整推理过程是折叠的**，只在状态条上留一句「已记录 N 条 · 点步骤卡片看完整过程」。点某张步骤卡片，弹窗里才逐条列出**该步真正调用到的本体要素**：`RULE_F01`／`F_12 批量发现`／`OT_CELL_MR` 证据条数／`INV_01、INV_09、INV_16` 校验／`A_01 建单 → TK-…`，以及时点推进与来源事实；那一步还在跑时，弹窗里的记录会跟着一条条长出来。记录来自运行期的 `tracker.tap`（旁听 `INV／RULE／TH` 的实际调用）与链自身的动作结果，**前端不复算、不解释、不补写**；顺序就是执行顺序，动作行以结果收尾。条头另有「跳至结果」，点了跳过逐步展示，一次跑满七步（各步记录照样记全，点卡片可看）。

**看结果的方式。** 主视图只有两块：状态条（过程）＋对象谱系图（结果，`GET /trace/cell` 的 `lineage`）。七步的正文不铺在页面上——点第 N 张步骤卡片弹出该步的「本体推理过程 ＋ 结果」，弹窗里的动作按钮照常可用，执行完弹窗切到下一步、状态条静默同步刷新（只刷到刚做完的那一步，不替你继续往下跑）。`Esc`／点遮罩／「关闭」收起弹窗。

**链的规矩。** 每一步都走本体自己的动作入口（`app.act`）：角色校验、INV 约束、审计留痕一律照旧，链不绕过任何一条，也不自己发明数值——必填参数全从本体事实推导（工单的诊断记录、方案的影响范围、现场回填记录、区域属性）。走到本体走不动的地方就停在那一步，写清是哪一步、哪条约束、缺什么。

| 小区（种子数据） | 链走到哪 | 为什么 |
|---|---|---|
| 崇贤达NF02H_222 | **七步走通** | 7 天全命中→天线下倾角过小→机械下倾 Δ=1°→派现场维护→现场回报 3°→4°→持续有效→关单入库（案例「有效可复现」） |
| 崇明医院门诊楼ND08H_12 | 止步于 ② 工单与定因 | 已建单，但 F_08＝未知：室分不适用宏站天线下倾角模型，转其他原因族 |
| 崇明体育中心NF02H_215 | 止步于 ① 发现与判定 | VIP 场景无适用派单规则（规则缺口），证据不足不建单 |
| 新河镇政府NF02H_58 | 止步于 ① 发现与判定 | 窗口内无 MR，证据不足不建单 |
| 港沿路NF02H_73 | 止步于 ① 发现与判定 | 命中天数不足门限，未达到派单条件 |
| 陈家镇北NF02H_196 | 止步于 ⑤ 实施回填（本体推不出）→ 人工接入后走完 | 种子里没有该小区的现场回填记录：F_11 的前提（现场实际值）缺失，推不出「达标且持续有效」；INV_07 不许用计划值代替，第 ⑥⑦ 步不执行；现场回报实测值后继续执行（见下） |

**人工接入：链停住不是失败，是本体推理的结论。** 执行中的停点只有两类（`stop.cause`）：

- **`cannot-infer` 本体推不出**——缺一条本体事实、证据不足、两来源冲突不能裁决、模型不成立（`INV_07／08／09／15`、`F_08` 不成立、`F_10` 未评估）。停点写清**期望什么**（`stop.expected`）、**缺什么**（`stop.gap`）；
- **`expectation-unmet` 结果不满足期望**——本体推出来了，但结论不达标（`F_10` 不通过 → 方案停草案、`INV_06` 不得批准；`F_11` 持续有效不成立 → `INV_10` 不得关单）。

发现阶段就不成立（`INV_16` 未达到、`INV_04` 状态不允许、已排除）是**终态**，不给人工入口——那些不是“执行中卡住”，也不能靠补一条事实继续。

停点把依据交代清楚：`stop.code`（哪条约束）、`stop.basis`（约束原文）、`stop.reason`（推理结论）、`stop.expected／gap`（期望与缺口）、`stop.human`（要谁、补什么、补完怎么继续；只有补得上事实的停点才有这一项）。前端在止步提示下面显示**人工接入处理**块：

- **本体依据**：`INV_07｜效果评估与复核使用现场回填的实际值，不使用计划值`；
- **期望**：`F_11 能判定效果「达标且持续有效」`；**缺口**：`F_11 的前提：现场实际值`；
- **推理结论**：无现场实际值，F_11 推不出效果 → 第 ⑥ 效果核验、第 ⑦ 闭环与案例不可执行（两格标「未执行」）；
- **需要人工**：现场维护人员 · 回报现场实测值；回报后从第 5 步继续；
- **处理入口**：填实际值、实施时间、回执、执行方 → 「现场回报并继续执行」（`POST .../facts/field-executions`，只补来源事实，身份按 A_06 的角色校验：现场维护人员／地市优化工程师）；或处理完后点「处理后继续执行」，重跑同一条链（幂等：停点之前的步骤静默重放，从 ⑤ 接着走）。

演示路径：点开 **陈家镇北NF02H_196** → 链走完 ①②③④（机械下倾 Δ=1°、派给现场维护人员）后停在第 ⑤ 步 → 现场回报 3°→4° → 继续执行 → ⑥ 持续有效 → ⑦ 关单并入库（案例「有效可复现」）。测试第 14 组第 ⑨ 段断言这条路径，以及“非现场角色不能替现场上报”。

**这个演示固定从 2026-09-11 09:00 起。** 它的 MR 故事是 09-04～09-28，发现窗口跟着判断时点走；先跑别的小区（尤其七步走通的崇贤达）会把判断时点推到 09-29，再点它就会在第一步判“未达到”。所以大屏提示上给了「从 09-11 重演」（重建运行时回到种子时钟与种子数据，再打开该小区）；如果已经点进去停在第一步，止步提示下面也有同一个按钮。这不是把时钟偷偷拨回去，而是明确重演一次。

**委托与自动的边界。** SPEC §自动与人工边界规定：可自动的是 F_12 发现、A_01 建单、A_02 规则定因、A_07 写效果；须人工确认的是 A_03 确认／排除、A_05 确认并派单、A_08 关闭、A_09 入库；天馈类措施一律派给现场维护人员执行、不得自动执行（INV_05）。链走完须人工确认的那几步时，**以本体动作表允许的角色委托执行**，并把这件事摆在明面上：

- 报告里这几步标 `humanGate`，界面显示「委托」徽章；
- 动作审计里执行身份记为「自主决策体」，角色记为实际生效的角色（地市优化工程师／优化主管／优化专家）；
- 天馈类措施的执行方始终是现场维护人员，链不代为执行；
- `POST .../chain/run` 传 `{"delegate": false}` 时链停在第一个须人工确认的步骤，等人在界面上确认（测试第 14 组逐项断言）。

**判断时点会自己往前推。** 等现场回填记录到达、凑够效果后窗天数，都是时点问题：链把时点推到本体算出的最早可评估时刻，并在报告里记下每次推进的时点与原因（“等待现场回填记录到达”“后窗需满 7 天”“持续有效需满 14 天”）。推进用的是本体参数（`effectMinDaysAfter`／`effectSustainDays`）与派单规则的窗口天数，不是写死的日期。

**链是幂等的。** 重跑不重复建单、不重复写效果记录，只复述已走通的结果；已闭环的小区重跑直接给出“已执行完毕”。

## 问答

规则驱动、结果可复现（语义理解用哪种引擎由后端配置 `semantic_engine` 决定，见下文「大模型接入」；那是同一接口的另一种措辞来源，事实仍来自本体函数，**前端不显示引擎差异**）。回答只引用函数结果、对象、关系和 SPEC 的本体元数据，**每个数值和日期都要能追溯到本次引用的来源**（落地检查，测试判定）。规则引擎本身只执行 SPEC 授权给它的自动动作（A_01 建单、A_02 规则定因、A_04 生成方案、A_07 写入效果）；确认、审批、回填、关单、入库、裁定只提示所需角色与参数，不代办（INV_05）。回答中标出本次写入了什么、还有哪些待人工动作。任何本体要素（OT_／RT_／F_／A_／INV_／RULE_／TH）都可以直接问“是什么”，答案取自 SPEC。

**前端问答面板是只读的。** 它固定传 `readOnly=true`：即使本体授权优化本体自动执行的动作，在问答里也只提示“到决策流程的第几步点按钮执行”，不产生写入与审计——写操作一律在小区决策流程页完成。同时它带**当前小区上下文**（`cellKey`）：问句点名小区以问句为准，没点名但用了“它／这个小区／该小区／刚才那个”时指向当前小区（相对指代由后端 `src/qa.js` 解析，前端不猜）。`/qa/ask` 不带 `readOnly` 时按本体原有授权执行，供命令行与自动化用例使用。

**面板上有引子与推荐提问。** 面板顶部一句引子说明“我是谁、能问什么、回答依据什么”；底部是**推荐提问**（有当前小区时按这个小区生成：它的属性、它已经走完的决策全流程、它的根因／工单状态／效果；没有小区时给全局问题），点一下只是把问句填进输入框，由用户回车或点“发送”发起提问——不自动提交，避免误发。

**回答是流式送来的，并写明依据本体里的哪些资源。** 前端走 `POST .../qa/ask/stream`（SSE）：`meta`（引擎／阶段）→ `refs`（回答依据的本体资源）→ `delta`（增量文本，逐句）→ `done`（完整回答＋落地检查＋写入与待人工动作）。增量拼起来就是完整回答，与非流式接口给出的文字一致（测试逐字比对）。**数值落地检查在送出之前完成**：编造的数字／单号不会被送到界面上，整段回退规则原文。每条回答下面列出它依据的本体资源徽章（`OT_`／`RT_`／`F_`／`A_`／`INV_`／`RULE_`／`TH`），点徽章进右栏检查器看定义与校验点。

**新问法：“已经完成的决策全流程”。** 问某个小区走过了哪些决策步骤，规则引擎按本体执行链路逐步讲（每步的动作、执行角色、成功还是被哪条约束拒绝、关键数值与依据的函数），与「决策链执行」里每步的推理过程同源；没跑过流程的小区会说明只读发现的判定，并指明建单（`A_01`）之后才有后续步骤。

## 大模型接入（可选，OpenAI 兼容接口）

问答默认仍是规则驱动、可复现。**语义理解用规则还是用大模型，只是一个开关**；模型接入本地（或任意 OpenAI 兼容网关）走**配置文件**，填 `api_key`、`base_url`、`model_name` 等接入信息即可。

| 环节 | 谁来做 | 说明 |
|---|---|---|
| 听懂问题 | 规则引擎 或 大模型（开关） | 规则：意图与措辞都在本地，可测可复现；大模型：把口语、指代（“它”“刚才那个小区”）、多轮上下文解析成 `{意图, 小区, 日期, 要素编号}`，意图只能落在 SPEC 本体的 48 个意图里，认不出就 fallback，不硬塞 |
| 取事实 | 规则引擎 | 按意图换成标准问句调用 `src/qa.js`，只跑一次；函数结果、对象、关系、SPEC 定义与先前完全一致 |
| 说人话 | 规则 或 大模型 | 大模型模式下，把事实改写成工程师口吻的自然回答，禁止新增数字与编号 |
| 数值落地 | 本地校验 | 改写文本里的每个数字、小区名、单号都要能在本次事实来源中找到；出现编造内容先重试一次，仍不过就回退规则原文 |

### 配置文件：`config/llm.config.json`

把 `config/llm.config.example.json` 复制成 `config/llm.config.json`（实际配置含 api_key，已在 `.gitignore` 里），然后填：

| 字段 | 说明 |
|---|---|
| `semantic_engine` | **语义理解开关**：`rule`＝纯规则（默认，可测可复现）；`llm`＝大模型做语义理解（事实仍来自本体函数） |
| `api_key` | 接口密钥；本地服务不校验 Key 时可留空，另写 `enabled: true` |
| `base_url` | OpenAI 兼容地址，如 `http://127.0.0.1:8000/v1` |
| `model_name` | 模型名，如 `qwen2.5-7b-instruct` |
| `enabled` | 一般不用填：填了 `api_key` 就算启用；本地服务不校验 Key 时写 `true`；想彻底关掉写 `false` |
| `timeout_ms`／`temperature`／`max_tokens`／`retries`／`extra_headers` | 可选，按网关需要调 |

生效顺序：**代码入参 > 环境变量 > 配置文件 > 内置默认值**。配置文件路径可用环境变量 `LLM_CONFIG_FILE` 改。文件不存在或不是合法 JSON 时**不报错**：问答照常按规则运行，并在 `GET .../qa/mode` 里如实回报配置错误。

`GET .../qa/mode` 回报当前档位与模型可用性（供运维自查；前端不读它、不展示引擎差异）：

```json
{ "semanticEngine": "rule", "available": false,
  "llm": { "enabled": false, "model": null, "baseUrl": null, "configFile": "…/config/llm.config.json", "configError": null },
  "rule": { "enabled": true, "note": "规则引擎：意图与措辞都在本地，可测可复现" },
  "llmNote": "模型未配置（配置文件 … 的 api_key / base_url / model_name），问答按纯规则运行" }
```

### 命令行与自检

```powershell
# 方式一：配置文件（推荐，本地模型就填本地地址）
copy config\llm.config.example.json config\llm.config.json   # 填 api_key / base_url / model_name

# 方式二：环境变量（临时改配置、或在容器里注入密钥）
$env:LLM_BASE_URL="https://api.openai.com/v1"   # 也可用 OPENAI_BASE_URL
$env:LLM_API_KEY="sk-..."                        # 也可用 OPENAI_API_KEY；不配则纯规则
$env:LLM_MODEL="gpt-4o-mini"                     # 也可用 OPENAI_MODEL
# 可选：$env:LLM_TIMEOUT_MS=30000  $env:LLM_TEMPERATURE=0.2  $env:LLM_MAX_TOKENS=1200  $env:LLM_RETRIES=1
# 可选：网关需要额外请求头时 $env:LLM_EXTRA_HEADERS='{"x-api-key":"..."}'

node scripts/llm-check.js        # 自检：配置 → 最小对话 → JSON 模式 → 一次完整语义问答
node src/qa-cli.js --llm         # 命令行问答（加 --llm 才走大模型）
node web/server.js --port 27080  # 本体应用前端；右栏问答（语义理解引擎由后端配置决定，前端不暴露）
node test/llm.js                 # 用本地假服务测编排层与 OSDK 的大模型模式（不需要真 Key）
```

测试与本机大模型配置隔离：`test/run.js` 与 `test/business.js` 把 `LLM_CONFIG_FILE` 指向不存在的文件（见 `test/model-isolated.js`），因此断言里的意图与回答文本恒为规则引擎的确定输出，**跑测试不会真调付费网关**，也不会因为把 `semantic_engine` 切成 `llm` 就挂掉。大模型模式的契约（异步路由、退化回退、数值落地）由 `test/llm.js` 用本地假网关单独覆盖。

降级与标注：未配置 Key、接口报错、超时、返回内容编造数字时，一律退回规则原文，**前端不显示任何"模型未启用 · 已用规则回答""LLM · 模型名"之类标注**——引擎属于实现层，页面上只标"数值落地 ✓／✗"与引用来源，回答口径与规则模式完全一致。接口契约不受影响。

大模型不是另一套后端：它是同一个 OSDK 接口 `POST /qa/ask` 的可选模式（`mode=llm`），事实仍由本体函数给出，路径、信封与错误码与规则模式完全一致；**用哪种引擎由后端配置 `config/llm.config.json` 的 `semantic_engine` 决定**，前端不传 `mode`、也不展示引擎差异。原先把大模型接进页面的 `console/` 影子门面已整体删除，现在只有 OSDK 一套后端。

## 局限

- 本地仿真；MR、工参、告警、派单均为种子数据。构造数据只保证复现原文的覆盖率等数值（假设 A-S1、A-S2），不代表真实网络。
- SPEC 的核心规则与测试假设本身尚待业务确认，本应用的判断同样保持“待确认”。
- 4 张工单里只有崇明一张落在 SPEC 的原因与处置范围内；其余按 SPEC 的范围界定如实标为未达到或范围外。
- 问答是规则匹配，换一种问法可能识别不出意图；接入大模型时应保留“只引用函数结果和对象数据”与数值落地检查。
